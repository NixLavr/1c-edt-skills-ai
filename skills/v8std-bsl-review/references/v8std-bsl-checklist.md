# V8Std BSL Checklist

Эта выжимка нужна для быстрого ревью и исправления кода по стандартам 1С. Не пытайся механически переписать весь модуль под идеальный шаблон. Используй правила как приоритетный чеклист и подтверждай спорные решения по исходному коду.

## Основные источники

- Главный раздел стандартов: <https://its.1c.ru/db/v8std>
- Оформление модулей: <https://its.1c.ru/db/v8std/browse/13/-1/31/32>
- Использование прикладных объектов и универсальных коллекций значений: <https://its.1c.ru/db/v8std/browse/13/-1/31/34>
- Оптимизация запросов: <https://its.1c.ru/db/v8std/browse/13/-1/26/28>

## Что проверять в первую очередь

### 1. Структура модуля

- Код должен быть разбит на логические части и читаться сверху вниз.
- Экспортные процедуры и функции не должны быть перемешаны со служебными без причины.
- Обработчики событий платформы должны оставаться узнаваемыми и не терять стандартную сигнатуру.
- Клиентский и серверный код должен быть разделен осмысленно, без случайных директив.

### 2. Имена

- Имена должны быть понятными, без произвольных сокращений и двусмысленности.
- Процедуры называют действием, функции результатом или признаком.
- Булевы признаки и функции-предикаты должны читаться как проверка условия.
- Локальные переменные можно переименовывать смелее, публичные точки входа только после проверки мест использования.

### 3. Описание процедур и функций

- Экспортные и сложные методы должны иметь краткое описание назначения.
- У параметров должны быть понятные имена и предсказуемый порядок.
- Если параметр является структурой, должен быть понятен ее ожидаемый состав.
- Комментарии должны пояснять намерение, а не повторять код.

### 4. Экспортный интерфейс

- `Экспорт` применяют только там, где метод действительно является частью внешнего контракта.
- Не раздувай количество экспортных методов без необходимости.
- Старайся не прятать важные побочные эффекты в функциях, от которых ожидают только вычисление результата.

### 5. Исключения

- Не оставляй пустых блоков `Исключение`.
- Не проглатывай ошибки без лога, сообщения или повторного возбуждения.
- Не используй исключения как обычный способ ветвления логики, если можно проверить условие явно.
- При исправлении сохраняй диагностический контекст и не скрывай первопричину ошибки.

### 6. Запросы

- Отбирай и выбирай только действительно нужные данные.
- Параметризуй запрос, не собирай условия конкатенацией строк.
- Переноси отборы и группировки в запрос, а не в цикл по результату, если это безопасно.
- Строго избегай запросов внутри циклов. Создание `Запрос`, установка параметров и `Выполнить()` внутри `Для`, `Для Каждого` или `Пока` считай сильным антипаттерном.
- Вместо запроса в цикле предпочитай один пакетный запрос, временные таблицы, коллекцию ключей с последующей выборкой одним обращением, либо предварительное чтение данных в соответствие.
- С осторожностью меняй текст запроса: не ломай совместимость по именам полей, которые потом читаются в коде.

### 7. Переиспользование БСП

- Если БСП уже есть в проекте, сначала ищи готовый стандартный механизм в общих модулях и типовых паттернах БСП.
- Самописный код, дублирующий имеющийся функционал БСП, считай нарушением и кандидатом на замену.
- Особенно проверяй дубли в задачах логирования, длительных операций, временного хранилища, настроек, свойств объектов, печати, файловых операций, сообщений пользователю и служебных преобразований данных.
- Не тащи БСП в проект, где ее нет. Правило действует как "использовать, если уже доступно", а не "всегда добавлять зависимость".

## Приоритет исправлений

Исправляй автоматически:

- неудачные локальные имена;
- пустые или вводящие в заблуждение комментарии;
- очевидно лишние `Экспорт` у приватных методов, только если нет внешних вызовов в проекте;
- пустые обработчики исключений;
- очевидно избыточные поля в запросе;
- фильтрацию после запроса, которую безопасно перенести в сам запрос.
- очевидные запросы в цикле, которые можно безопасно вынести в одну пакетную выборку.
- локальные самописные утилиты, которые дублируют уже имеющийся функционал БСП в этом проекте.

Оставляй замечание вместо автоправки:

- для переименования экспортных методов;
- для смены сигнатур;
- для изменения контрактов структур параметров;
- для заметной переработки SQL-подобной логики запроса;
- для перехода на механизм БСП, если не подтверждено, что нужный модуль доступен и совместим по контексту;
- для случаев, где стандарт конфликтует с существующим публичным API.
